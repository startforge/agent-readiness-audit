# T-02 Tool Permission and Scope Checks

- Profile: core
- Risk: Critical
- Requirement: Every tool call passes through permission and scope checks.
- Applicability: The project has callable tools or external side effects.
- Check strategy: automated (AST call-chain plus tests/traces)
- Static evidence: Permission gate, allowlist, path or domain constraints (`authorize`, `PermissionGate`, allowlist).
- Structural evidence: The permission gate dominates tool execution with no bypass path. Comments and unused `authorize()` helpers cannot pass.
- Test evidence: Unauthorized and out-of-scope calls are rejected.
- Runtime evidence: The trace records the decision and refusal reason.
- Pass criteria: Structural evidence plus at least test or runtime evidence. Keyword matches cannot produce `pass`.
- Common false positives: Comments, unused `authorize()` calls, frontend-only restrictions, documentation-only claims.
- Common false negatives: A real gate in a shared middleware file that the executor does not name directly (manual review until deeper module resolution).
- Fixtures:
  - `fixtures/core-permission-pass` — gated executor plus unauthorized-call test; expected `pass`.
  - `fixtures/core-permission-partial` — gated executor without tests; expected `partial`.
  - `fixtures/core-permission-fail` — tools with no gate; expected `fail`.
  - `fixtures/core-permission-bypass` — `authorize` exists but `executeTool` does not call it; expected `fail`.
  - `fixtures/core-permission-comment` — gate exists only in a comment; expected `fail`.
  - `fixtures/core-permission-py` — Python AST equivalent of the pass fixture; expected `pass`.
- Remediation and acceptance: Route every tool call through a permission and scope gate. Unauthorized and out-of-scope calls are rejected; traces record allow/deny; no bypass path exists around the gate.
